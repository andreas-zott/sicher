1. Überblick

Das Portal ist eine statische Web-App ohne eigenes Backend und ohne Datenbank. Jede Seite ist eine HTML-Datei; alle Berechnungen, PDFs und Speichervorgänge laufen im Browser des Geräts. Ausgeliefert wird über GitHub Pages unter dem Pfad /sicher/. Das Portal lässt sich auf iPad und iPhone zum Home-Bildschirm hinzufügen und funktioniert nach dem ersten Aufruf auch offline.

Gestaltung „Leitstand“: gleiche Schrift (Space Grotesk) und Markenfarbe wie ASiC Handel. Standard ist der dunkle Modus; über den Schalter oben rechts lässt sich auf hell umstellen. Ausdrucke sind immer hell.

4. Datenfluss und Speicherung

Zwischen den Seiten

  • Checkliste/Audit → Fotoformular: Marktnummer, Name und SiFa als URL-Parameter (foto.html?marktnummer=…&name=…&sifa=…).
  • Checkliste → Maßnahmen-Auswertung: Die Maßnahmen werden vor dem Öffnen in localStorage geschrieben (massnahmen_uebergabe); zusätzlich wird postMessage versucht.
  • Audit → Maßnahmenplan: über localStorage (massnahmenplanData). Im Plan bearbeitete Angaben derselben Begehung (gleicher Markt und gleiches Datum) werden beim erneuten Öffnen übernommen.
  • Audit → NAS: „Direkt auf NAS speichern“ sendet die Begehung als JSON per fetch() an save.php. Pflichtangaben: companyInfo.datum und companyInfo.marktnummer.
  • Übersicht: liest checkliste_stand_v2 für das Statusfeld „Angefangene Checkliste“ und prüft, ob der Service Worker bereit ist.

Gespeicherte Daten im Browser

6. Offline-Betrieb und Updates

service-worker.js ist der einzige Service Worker des Portals (Geltungsbereich /sicher/). Anfragen an die Unterprojekte bearbeitet er nicht.

  • Seiten, Stylesheets, Skripte, JSON: Netz zuerst. Ist das Gerät online, kommt immer der aktuelle Stand vom Server, und die gespeicherte Kopie wird aufgefrischt. Offline oder nach 4 Sekunden ohne Antwort wird die gespeicherte Fassung geliefert.
  • Schriften, Bilder, Bibliotheken: Speicher zuerst, weil sie sich selten ändern.
  • Installation: Beim Einrichten einer neuen Version werden die Dateien unter Umgehung des Browser-Zwischenspeichers geladen (cache: 'reload'), damit keine bis zu 10 Minuten alte Fassung von GitHub Pages übernommen wird.
  • Automatisches Neuladen: Übernimmt eine neue Version die Kontrolle, lädt js/common.js die Seite einmal neu. Die Prüfung auf eine neue Version erfolgt bei jedem Aufruf ohne Zwischenspeicher (updateViaCache: 'none').
  • Aufräumen: Beim Aktivieren werden nur eigene alte Caches (sicherheit-cache-…) gelöscht; die Caches von ASiC Handel, GBO und Audit-2026 bleiben unberührt.

7. Pflege: Fragen, Zugänge, Versionen

Frage der aktuellen Checkliste ändern oder ergänzen

In js/checkliste-daten.js hat jede Frage eine feste id, unter der die Antworten gespeichert werden:

{ "id": "1.22",
  "frage": "So formulieren, dass „Ja“ = in Ordnung bedeutet?",
  "massnahme": "Text, der bei „Nein“ in die Maßnahmentabelle kommt." }
Neue Fragen bekommen eine neue id. Bestehende ids nicht umnummerieren – sonst landen gespeicherte Antworten bei der falschen Frage. Die Anzahl im Kopf der Checkliste wird automatisch gezählt.

Wird in einer Frage oder Maßnahme eine neue Vorschrift, Regel oder Norm genannt, diese auch in quellen.html in der passenden Gruppe ergänzen (Kurzbezeichnung, Titel, Link, „Verwendet in“).

Zugang anlegen

In index.html steht pro Zugang nur ein SHA-256-Hash von name:passwort:sicher-portal-v1 (Name in Kleinbuchstaben). Neuen Hash bilden, z. B. in Python:

import hashlib
print(hashlib.sha256("name:passwort:sicher-portal-v1".encode()).hexdigest())

und in die Liste ZUGANG_HASHES eintragen.

Neue Version veröffentlichen

  1. Versionsnummer gleichlautend erhöhen in service-worker.js (APP_VERSION), js/common.js (APP_VERSION) und manifest.json (version).
  2. Neue Dateien, die offline verfügbar sein sollen, in FILES_TO_CACHE in service-worker.js eintragen.
  3. Dateien hochladen. Gelöschte Dateien im Repository von Hand entfernen – das Hochladen löscht nichts.

Reine Text- und Gestaltungsänderungen an Seiten, CSS oder JS sind auch ohne Versionssprung sofort sichtbar (Netz zuerst). Die Versionsnummer ist nötig, wenn sich Schriften, Bilder oder Bibliotheken ändern.

8. Bekannte Grenzen

  • Zielplattform: iPadOS/iOS Safari (Teilen mit Dateianhang, Kamera, Touch). In anderen Browsern fällt „PDF teilen“ auf einen normalen Download zurück.
  • Anmeldung: Die Prüfung erfolgt nur im Browser. Im Quelltext stehen keine Namen oder Passwörter, aber alle Seiten sind direkt aufrufbar und kurze Zahlencodes lassen sich durchprobieren – eine organisatorische Hürde, kein Zugriffsschutz.
  • NAS-Speichern im Audit: save.php liegt nicht im Hauptordner des Repositorys. Es funktioniert nur, wenn die Seite über die Synology (bzw. Tailscale) aufgerufen wird oder in ASiC Handel eine NAS-Adresse hinterlegt ist; über GitHub Pages laufen keine PHP-Skripte.
  • Audit-Fragen: Antworten werden nach Position gespeichert. Fragen in audit.html daher nicht löschen oder umsortieren, sonst verrutschen gespeicherte Audits.
  • Theke/Metzgerei: erzeugt bei „Nein“ keine Maßnahmen und hat keinen PDF-Export (nur Druck).
  • Fotos: Sehr viele Fotos (deutlich über 20–30) verlangsamen die PDF-Erzeugung.
  • Gerätespeicher: Daten im Browser gehen verloren, wenn die Websitedaten gelöscht werden; sie werden nicht zwischen Geräten abgeglichen.
